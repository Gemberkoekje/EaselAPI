# M9 — The MCP server

The brief's last item, in one sentence: *one tool per CLI verb, plus `look`,
`preview` and `compare` returning their images inline* — and the rule that put it
last, which is that **anything changing the API lands before the server exposes
it**. That list (`ENGINE_CHANGES.md`, and the costing rule out of `REHEARSAL6.md`)
is empty, so this is the first change in the repo that is allowed to add nothing
to the engine at all.

It doesn't. **No golden image moved, both samplers are byte for byte unmoved, and
nothing in this milestone renders a pixel differently** — there was no regeneration
to look at, because there was nothing to look at. The evidence here is therefore of
a different kind from M7's or M8b's: not a picture, but whether the wrapper is as
thin as it claims and whether the one translation it has to do is faithful.

```bash
pip install -e ".[dev,mcp]"
pytest -q tests/test_mcp.py        # 73 tests
easel-mcp --dir .                  # or: python -m easel.mcp_server
```

## 1. It is the CLI, and that is the whole design

The brief's priority order is library, then CLI, then server, and the CLI is a thin
wrapper over `Session`. This is a second wrapper of the same thickness rather than a
third interface: same verb names, same argument names, and **the `.easel` file is
still the only state**. Every tool loads it, does one thing, and saves it back, so a
painting can be worked on through the server, through the shell and from a plain
Python script in any order, in any mix.

That is asserted rather than asserted-in-prose. `test_every_cli_verb_is_a_tool`
reads the CLI's own subparsers and requires a tool for each, so a verb added to the
shell later cannot quietly fail to arrive here — and it pins the difference too:
the only tools that are *not* CLI verbs are the three below.

Two things that were printed are now returned, so that the two surfaces cannot
drift:

- `reference_text()` — what `easel brushes` prints, and what the `brushes` tool
  returns. One list of pigments, or the second one is wrong the first time a pigment
  is added. `test_the_reference_is_the_one_the_cli_prints` runs the CLI, captures
  its stdout, and compares all three.
- `run_script()` — the exec-with-the-API-in-scope, and the rules about what gets
  saved when a script raises, calls `exit()`, or does not parse. Those rules were
  four separate `REVIEW.md` findings; a second copy of them is a second place for
  them to rot. The CLI prints its `ScriptResult`; the server returns it.

## 2. What it adds: the picture comes back

`look`, `preview`, `rehearse`, `compare` and `prepare` return their PNG beside the
path they wrote it to. The brief names three of those; `rehearse` and `prepare`
arrived after it was written and their whole output is a picture to read, so
withholding theirs would have been a distinction without a reason.

Measured on a 112-mark, 900×675 painting:

| | |
|---|---|
| `look` | 1921 ms, 372 KiB of PNG inline |
| `preview` | 1873 ms, 370 KiB |
| `rehearse` | 2396 ms, 368 KiB |
| `cost` | 292 ms |
| `log` | 285 ms |

**The cost is in the file, not in the server**, and it is worth writing down
because it is the one thing about this milestone that is worse than it should be.
Of `look`'s 1921 ms, 136 ms is the render and **1375 ms is writing the session back**
— which a look does only because it moved the look counter by one and stored what
the next `diff=True` compares against. `easel look` pays exactly the same 1375 ms
for exactly the same reason, so this is not a regression; it is a thing the server
makes conspicuous because looking is what it is for. 774 ms of it is
`savez_compressed` recompressing 113 time-lapse thumbnails that did not change.

The fix is in the save format and not in the server, so by the brief's own rule it
does not belong in M9. It is written up under *Still open*.

## 3. The three questions, and the one thing that can drift

`preview`, `rehearse` and `cost` answer where a mark goes, what it will look like,
and what it charges. They are not CLI verbs and they are here because a painter
whose client speaks MCP has no other way to reach them — `REHEARSAL4.md`'s pass
session called `preview` once and `rehearse` never and spent 138 of 299 strokes
repainting one table, and `REHEARSAL6.md`'s budgeted 4 strokes for a curved ribbon
and paid 21.

They introduce a problem the CLI does not have. Through this server **a plan is
checked in JSON and painted in Python**, so the plan that was priced and the plan
that lands are two different texts, and `session.py` says in as many words why that
is the failure mode to design against: *"a plan that has to be rewritten between
checking it and painting it is a plan that will drift."*

So each of the three hands back the call it just priced:

```
> cost(session, plan={"shape": {"blob": "D5", "radius": 0.12, "seed": 3},
                      "brush": "bristle", "color": "dark", "size": 0.05,
                      "direction": "axis"})

8 stroke(s). Paints as:

s.block_in(blob(cell('D5'), radius=0.12, seed=3), brush='bristle', color='dark', size=0.05, direction='axis')  # 8
```

The price rides in a trailing comment and the header is a `#` line, so the whole
block below the first line is valid Python and pastes into `run` as it stands —
`test_the_echoed_python_is_python` compiles it.

**And it is checked by being run.** `test_the_quoted_price_is_what_the_echoed_python_pays`
takes thirteen plans covering every place form, quotes each, feeds the quote's own
output to `run`, and counts what came off the log. Sixteen forms were measured this
way while it was being built; zero mismatches, then and now:

```
quoted   8  painted   8  s.block_in(blob(cell('D5'), radius=0.12, seed=3), ...)
quoted  28  painted  28  s.block_in(ribbon([(0.2, 0.8), (0.5, 0.5), (0.8, 0.42)], width=0.09), size=0.03)
quoted  16  painted  16  s.block_in(hull([cell('D4'), cell('F6'), (0.2, 0.9)]), size=0.06)
quoted  25  painted  25  s.sweep([(0.15, 0.75), (0.5, 0.62), (0.85, 0.7)], into='down', depth=0.2, cross=25, ...)
quoted   5  painted   5  s.sweep(blob(cell('D5'), radius=0.15, seed=1), depth=0.12, size=0.04)
```

## 4. A place, as it arrives over the wire

`NOTES.md` set this as the one new thing M8 adds to the server's design: *a place is
a name, a cell, a span, a rectangle or a list of points, and `sweep` takes the
same*. All five are here, and a sixth the wire needs and Python does not:

```text
"upper-band"                                    a named region
"D4"                                            one grid cell
"C3:F6"                                         a run of cells
[0.10, 0.10, 0.45, 0.30]                        a rectangle
[[0.2, 0.2], [0.6, 0.15], [0.7, 0.5]]           an outline
{"blob": "D5", "radius": 0.12, "seed": 3}       a shape builder
```

The sixth exists because the first five are not enough. `regions.py` is there so
that a painter does not have to invent coordinates, and a JSON surface that can only
carry an outline hands back exactly that job — the painter would be writing point
lists to describe a mass it can name. So a place object carries one builder's name,
its first argument under that name, and its own keywords beside it, and it reads as
the call it becomes: `{"blob": "D5", "radius": 0.12, "seed": 3}` is
`blob(cell("D5"), 0.12, seed=3)`. `test_a_place_arrives_as_the_shape_the_python_builds`
checks each form against the object the Python builder returns, bounds and points.

A place object carries the *builder's* arguments and nothing else. A mass that wants
a brush is written the long way, under `shape`, so there is never a question of
whose keyword a keyword is — and `{"blob": "D5", "brush": "bristle"}` says so
rather than guessing.

JSON has one ambiguity Python has not: `[[x, y], ...]` is both a path and an
outline, and the type decides it in Python. Here **a bare list of points is a mark**,
matching what `_plan_specs` does with a bare path, and a mass is written
`{"shape": [[x, y], ...]}`. A place on its own — a string, or a shape object — is a
mass, matching what `_plan_specs` does with a bare `Region` or `Polygon`.

## 5. Four defects, all of them "the wire is not Python", all found by driving it

None is in the engine. Two were in code written for this milestone; two are places
where an API that is unambiguous in Python is ambiguous over JSON, and the server is
where that has to be resolved. All four were found by calling the tools, not by
reading them.

- **A shape object on its own was not a mass.** `{"hull": [[...], [...], [...]]}`
  fell through to the stroke branch and complained that a shape had no points, while
  the bare `"D4"` beside it in the same list worked. The rule is one rule — a place
  on its own is a mass — and it now has one implementation.
- **A mixed `hull` broke the echo.** `_py_place` worked out its head argument before
  deciding whether the builder takes a *list* of places, so
  `hull(["D4", "F6", [0.2, 0.9]])` went down the rectangle branch and tried
  `float("D4")`. The quote was right and the Python beside it raised — which is the
  exact failure the echo exists to prevent, arriving in the echo itself.
- **`grid="none"` drew a grid.** `render_look` draws the coarse grid for *any*
  truthy string, which is right in Python — where the two spellings are in the
  docstring in front of you — and wrong on a wire a client fills in from a schema.
  `"none"`, `"off"` and `"false"` now mean what they say, `"sideways"` is named, and
  the test asserts it on the pixels, because the failure it guards against is a call
  that succeeds and returns the wrong view.
- **A misspelled plan key priced happily and then raised when pasted.** `cost` walks
  the passes and never touches the brush overrides, so `{"shape": "D4", "sze": 0.04}`
  quoted a mass at the default brush size and the echoed Python beside it raised in
  `run`. That is the whole failure mode this milestone is built to prevent, arriving
  as a *price*. A plan is now checked against what its call takes before it is
  priced — the principle `session.py` already states for `sweep`: a plan that cannot
  be swept raises when it is priced, not when it is paid for. The accepted keys are
  read off the signatures and `Brush`'s fields rather than listed, so they follow the
  API instead of having to be remembered when it moves.

A fifth thing was made bad input rather than a crash: a bad keyword to a *builder*
now names the builder and the keyword, instead of a traceback.

## 6. What it must not do

Two properties matter more here than anywhere else in the repo, because the server
reloads the session between every call and that is exactly where a stream state gets
lost:

- **A rehearsed mass is the painted one, across the reload.** `rehearse` writes,
  the session is saved, `run` loads it and paints the echoed call, and the two
  renders are compared pixel for pixel. Identical, max delta 0.
- **Asking costs nothing.** Three rounds of `cost` + `preview` + `rehearse`, each
  with its own save and load, and the painting that follows is byte for byte the one
  that would have been painted without asking at all.

Both come from the engine (`_trial_session` holds a *copy* of the stream state — the
half of `engine_changes/` that mattered), and both could have been broken by the
server without the engine noticing. `test_a_rehearsed_mass_is_the_painted_one` and
`test_planning_does_not_spend_the_stream` are the ones to keep.

## 7. Failures say the engine's own words

The SDK withholds an exception's message from the client and logs it server-side,
which for a painter means a console nobody is reading. So the server catches the
same set the CLI catches and says the same `easel: ...` line for the same input:

```
easel: "Unknown region 'Z9'. Use a name (all, bottom, ...), a grid cell like 'D4', ..."
easel: sweep(cross=0.0) is how far the second set of passes leans off the boundary...
easel: [0.1, 0.2] is not a place. Give a named region ('upper-band'), a grid cell...
```

Anything outside that set is a crash rather than bad input, and gets its type and
traceback rather than the generic "error executing tool" — a withheld message is a
message nobody sees.

## Trust

`run` executes Python sent by the client. That is the same trust boundary
`easel run` has always had — running the painter's own script is the point, and it
is how every mark is made — but it is worth saying plainly rather than leaving
implied: launch this for a painter you would hand a shell to, and no other. It is
not sandboxed and nothing here pretends otherwise.

## Still open

- **A look costs 1.4 s of session write to move a counter by one.** Measured above.
  113 time-lapse thumbnails and three canvas planes are recompressed because
  `_look_counter` and `_last_look` changed. `easel look` pays the same. The fix is
  in the save format — the frames and the snapshots do not change on a look and
  could be left alone — and a save-format change is an engine change, which by the
  brief's own rule goes in front of a server rather than inside one.
- **A prepared reference does not survive the save.** `Session.save` does not write
  `_preparation`, so `prepare` through the server (or through the CLI) leaves the
  table and the overlay but not the areas: `ref_region`, `ref_outline` and
  `ref_shape` are reachable only inside the same `run` script that prepared. Not
  introduced here and not a parity gap — the CLI has behaved this way since M6 — but
  the server makes it easier to trip over, because every call is a fresh load.
- **The `mcp` dependency is pinned `>=2,<3`.** 2.x is where `FastMCP` became
  `MCPServer`; 1.x will not import `easel.mcp_server`. It is an opt-in extra, like
  `mixbox`, and the main CI job deliberately installs without it — which is what
  proves the module degrades to a clean skip rather than an `ImportError`.
