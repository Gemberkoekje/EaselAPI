# Build brief: headless painting API ("Easel")

You are building a tool that lets an AI agent paint — not draw, not rasterize, but paint: brushes, paint load, wet and dry, canvas texture, mistakes that stay. The tool is headless (no GUI, no Krita), produces PNGs, and is meant to be driven from a Claude Code session by an agent that can look at its own work between strokes.

Two things are being built:

1. **The engine + API** — a library and thin CLI.
2. **The painter's guide** — a document that teaches a *fresh* agent, with no knowledge of the engine internals, how to paint with it well.

The second is not an afterthought. The engine will be judged by what a fresh session paints with only the guide in hand.

## The experiment this serves

After the build, a **separate, fresh Claude Code session** receives only: the installed library, the painter's guide, a canvas size, and a reference photo of an ordinary object. It is asked to paint a faithful copy. When done, it is told: "Now paint something of your own. No subject, no theme, no prompt." Nothing else. The human watches the output and does not intervene.

Design every decision toward that: the painter is a language model that reasons well, sees images well, and is bad at absolute pixel coordinates.

## Decisions already made (override only with a stated reason)

- **Language:** Python 3.12+, numpy for all pixel work. No native dependencies that are painful on Windows (no GObject/libmypaint bindings). Pillow only for PNG I/O and text overlays.
- **Interface, in order of priority:** (1) Python library, (2) thin CLI wrapping it, (3) MCP server — optional, last, only if 1 and 2 are solid.
- **Canvas model:** single canvas, no layers. Real painting has no layers; the painter learns to work in passes instead. Undo exists (snapshots), but is documented as "scraping the canvas," not a free action.
- **Coordinates:** normalized 0.0–1.0 on both axes, origin top-left. Never expose raw pixels to the painter. Add named-region helpers on top (see Composition).
- **Determinism:** every session takes a seed; the same script with the same seed produces the same PNG.
- **Feedback loop:** `look()` is the most important function in the API. Treat it that way.

## Architecture

### Canvas
- Float32 RGB in linear light, converted to sRGB only at export.
- Additional per-pixel channels: `wetness` (0–1), `thickness` (paint height, for impasto and dry-brush behaviour), and from M6 `sketch` (graphite, 0–1): a channel, not a layer. Paint covers it in proportion to what has landed, so it shows through thin paint and where the ground shows, and is gone under an opaque mass.
- Procedural canvas/paper texture: a height map that modulates paint deposition. Selectable at creation: smooth panel, linen, rough paper. Ground colour selectable (white, toned grey, burnt-sienna wash).

### Brush engine
Dab-stamping along a path (this is how MyPaint and Krita work; do not attempt fluid simulation).
- A **stroke** = a path (list of normalized points, smoothed with Catmull-Rom or similar) + a brush + a pressure profile.
- A **brush** = a tip mask + dynamics. Tip masks are procedural: round soft, round hard, flat (rectangular, rotates to follow stroke direction), bristle (flat with random striations and gaps — this one matters most for looking painterly), palette knife (hard-edged, drags rather than deposits).
- **Dynamics:** size, opacity, hardness, spacing (as fraction of size), jitter, paint load (how much paint the brush carries — it runs out along a stroke), pressure curve (default: taper in and out), speed-to-size mapping.
- **Pressure profile:** the painter gives either a scalar, a list, or a named profile (`taper`, `press_in`, `lift_off`, `even`).
- Deposition is modulated by canvas texture: low paint load on rough texture = dry brush effect for free.

### Paint behaviour
- **Wet blending:** when a stroke lands on wet pixels, it mixes with what's there proportionally to wetness rather than covering it. `dry()` reduces wetness across the canvas (all or a region). Wet also decays slowly per stroke count so the painter doesn't have to manage it constantly.
- **Colour mixing:** naive RGB averaging turns everything grey-brown. Use a pigment-style model. Prefer the `pymixbox` package (Mixbox; verify licence suits this project) — if unsuitable, implement a simple subtractive approximation and document its limits. Mixing applies both on the canvas (wet blending) and on the palette (see below).
- **Smudge / blend tool:** picks up colour from the canvas and drags it. Distinct from painting.
- **Glaze:** a thin transparent layer over dry paint — implemented as low-opacity deposition that does not raise `thickness`.
- **Impasto is optional.** Track `thickness` and offer a subtle relief shading in export if it's cheap; do not let it eat the schedule.

### Palette
A palette object the painter mixes on, like a real one: a small set of starting pigments (a warm and cool of each primary, plus white, a dark — no black by default), `mix(a, b, ratio)`, `tint`, `shade`, `desaturate`, and named slots so the painter can say `palette["sky"]` later. Mixing on the palette uses the same pigment model as the canvas.

### Composition helpers (this is where the model's weakness lives)
- Named regions: `region("top-left")`, thirds grid, golden-section lines, `horizon(0.4)`.
- Relative placement: `below(region, amount)`, `between(a, b)`.
- Shape primitives that emit *strokes*, not fills: `fill_region_with_strokes(region, brush, colour, direction, density)` — block-in as a painter does it, with visible brushwork.
- Value tools: `values_only()` view in `look()` (greyscale), so the painter can check its value structure the way a painter squints.
- Landmarks (M6): `mark(name, x, y)` records a named point, looks can show every mark on both panels, and `pt(name)` uses one in a path. Six or seven verified points are a drawing; the masses are hung on them.

### look()
Returns a PNG path (and, in the MCP variant, the image itself). Options:
- `scale`: default downsampled to ≤1024px on the long side.
- `grid`: overlay a labelled grid (A–H × 1–8) so the painter can say "the dark shape near D6" and later target `cell("D6")`.
- `region`: crop to a named region at full resolution.
- `values`: greyscale.
- `side_by_side(reference)`: for the copy stage.
- `diff`: highlight what changed since the last `look()`.
- `region` together with `reference`: crop **both** panels to the same region, enlarged to a readable size; `grid="fine"` labels tenths inside the crop, so a place inside a cell is read off as `cell("D4").point(0.3, 0.6)` rather than estimated. (M6)
- `preview(strokes, reference=...)`: the points and brush widths of intended strokes drawn over both panels, painting nothing and logging nothing. (M6)
- `compare(reference)`: per cell, the mean value of the reference and of the canvas and their difference, as a table and as a heat map beside the greyscale comparison. (M6)

### History
Every stroke is logged as data. The whole painting is replayable from the log + seed. `undo(n)` restores a snapshot. Export a time-lapse (contact sheet or GIF) from the log — cheap and very useful for the human watching.

## CLI
`easel new`, `easel run script.py`, `easel look [--grid] [--values] [--region R]`, `easel undo N`, `easel export out.png`, `easel timelapse out.gif`. Session state lives in a single `.easel` file (npz). The CLI exists so a painter can work in small increments from a shell without holding a Python process open.

## The painter's guide (deliverable, `PAINTER.md`)
Written for an agent that has never seen the source. Contents:
- The API, briefly, with 5–6 complete tiny examples.
- **A painting workflow**, not a tool reference: tone the ground → establish the big value shapes with a large brush → check values with `look(values=True)` → refine mid-tones → edges (lost and found) → highlights last, smallest brush, least strokes. Say explicitly: look every 5–15 strokes; a stroke you didn't look at was a guess.
- What the model is bad at and what to do about it: don't reason in pixels, use regions and the grid; don't draw outlines and fill them, paint masses; when something is wrong, paint over it rather than undo.
- What each brush is for, in one line each.
- Nothing about what to paint. The guide must not contain example subjects that would bias the unprompted stage. Use abstract exercises (value scales, edge studies) for its examples.

## Build order

1. **M1 — Foundation.** Canvas, round brush, straight and curved strokes, `look()`, PNG export, seed. Deliver a brush sampler sheet (`samples/brushes.png`): every brush at three sizes, three pressure profiles, on each canvas texture. This sheet is your primary test artefact; regenerate it after every engine change and actually look at it.
2. **M2 — Painterly.** Flat and bristle tips with direction following, paint load and run-out, canvas texture modulation, wet blending, `dry()`, pigment mixing, palette.
3. **M3 — Composition and looking.** Regions, grid, relative placement, stroke-based block-in, values view, side-by-side, diff, history and time-lapse.
4. **M4 — CLI and guide.** CLI, `PAINTER.md`, install instructions (`pip install -e .`).
5. **M5 — Rehearsal.** Run the experiment protocol yourself on a reference image, as if you were the fresh session, using only `PAINTER.md`. Every time you reach for source code or internal knowledge to get unstuck, that is a gap in the guide — fix the guide, not your painting.
6. **M6 — Precision.** The second rehearsal (`REHEARSAL2.md`) produced a recognisable *scene* and not a recognisable *sitter*, and every cause traced to one gap: the painter can name a place to within one grid cell, and a feature is smaller than a cell. Everything in this milestone is looking and measuring; nothing in it places a stroke for the painter. It comes before the MCP server because the server exposes the API, and this is what changes the API.
   - **Golden images first.** Before anything else in this milestone: a fixed script of strokes on each texture, hashed, plus the sampler, so that any change to what a mark looks like fails loudly. The review loop has asked for these since M2 and they still do not exist. M6 touches the canvas and the renderer and M7 changes every stroke, so they go in before either.
   - **Matching crops.** `look(region=..., reference=...)` crops both panels to the same region, enlarged, with `grid="fine"` for labelled tenths inside the crop. Precision below the cell becomes reading a label, which the painter does reliably, instead of estimating a fraction, which it does not.
   - **Stroke preview.** `preview(...)` draws intended points and brush widths over both panels without touching the canvas or the log. A guess is checked against the photograph before it is paid for in strokes, so the paint–look–repair loop becomes plan–check–paint.
   - **Landmarks.** `mark(name, x, y)`, shown on looks, used with `pt(name)`. The drawing of a head or a hand is six or seven named points verified with the preview.
   - **Value numbers.** `compare(reference)`: per-cell mean value for both and the difference, table and heat map. Mean colour per cell too, coarse on purpose — a measuring stick, not a colour picker. The number that matters is `0.10`, the guide's own threshold for two masses reading as one.
   - **Reference preparation**, a separate tool: `easel prepare ref.jpg` and `s.prepare(reference)`. Programmatic, no model, no LLM: quantise the reference in a perceptual colour space, label connected areas, merge fragments below a minimum size, outline each area and number it. Output is an overlay the painter looks at — outlines and numbers on the reference, the same outlines on the canvas — and a table per area: share of the picture, cells covered, mean value and colour, neighbours, and how hard its edge is against each neighbour (mean gradient along the shared boundary). `ref_region(n)` gives an area's bounds, `ref_outline(n)` its polygon as normalised points. Granularity is a parameter (coarse, five to eight masses; medium, about twenty), and the painter can `merge` and `split` areas, because the automation will join hair to a wall of the same brown and cut a coat along its folds. The painter's job is to say "area 5 is the hair, less the strip that is really wall", not to accept the map. The outlines are for looking and naming. Whether the engine also gets a polygon block-in is a decision for the human: it would make a copy faster and make it partly traced, and a rehearsal that uses it must say so.
   - **Pencil underdrawing.** A painter does not start on a blank canvas; the sketch is the first pass, and making it disappear is the painting. `pencil(points)` draws a thin graphite line into the `sketch` channel: no paint, no wetness, no thickness, broken by the canvas tooth like a real pencil, not counted as a stroke. `sketch(reference, level=...)` lays the outlines from `prepare` as pencil in one call — an *assisted* mode, off in the headline run, see the definition of done; `erase(region)` clears the sketch where the painter disagrees with it; `sketch_lines()` returns every line as normalised points, so a stroke can be aimed at a line, swept along it, or ignore it. `look(sketch=False)` hides it, `export(sketch=True)` keeps whatever paint has not covered. The lines are not the painting: the guide must say to paint *through* them, not up to them, to erase before painting rather than argue with a line while painting, and that hair drawn along the pencil line still has to go every which way. For the unprompted stage the pencil is the painter's own: sketch the masses, look, adjust, then block in.
   - **Liner.** A brush preset for fine lines: `round_hard` at `size=0.005`, hardness `1.0`, no jitter or size jitter, slow run-out. The second rehearsal's eye test showed lines render at their nominal width down to three pixels, so nothing new is needed in the engine — only one word for what today takes four overrides.
   - **Rehearse.** `rehearse(strokes, region=..., reference=...)` paints the strokes on a *copy* of the canvas and returns a look of the region, enlarged, with the reference's matching crop beside it; nothing is committed and nothing is logged. The preview shows where a mark will go; the rehearsal shows what it will look like. A feature the size of an eye can be tried three ways and judged before a stroke is spent, which is what a painter's scrap of canvas is for, and it removes the last reason to reach for `undo`.
   - **Crops at feature scale.** The enlarged crop must show a single grid cell at five times or more, and `preview`, `rehearse` and `compare` must all accept the same `region=` and `reference=` so the whole loop — name a place, plan a mark, try it, judge it against the reference — runs at the scale of the feature.
   - **Guide.** A drawing step in *Working from a reference*, between the masses and the features: landmarks first, verified, then masses hung on them; how to read a place inside a cell; when to stop measuring.
   - Then run the M5 protocol again, fresh session, same reference. That run is the measurement, and the definition of done below says what it must show.
   - **Run and not passed** — `REHEARSAL3.md`, three fresh sessions. The tools reach: the sitter has an eye with a lid, an iris and a catchlight where the M5 run had a smear, and the smallest thing placed on purpose was 3.6 px, about a fortieth of a cell. The copy stage passes recognition (a mug), the 295-stroke budget and the rejected marks, and **fails on value**: five of thirteen cells on the object are the painter's own error and every one is too light. Three engine changes came out of it (`REVIEW.md` 20-22) and eight guide edits, and M6 wants one more run to see whether the value error goes away.
   - **Two findings from the human that the three sessions missed**, both in `rehearsal3/HUMAN_NOTES.md`: every mass is laid along the canvas's axes, and nothing ever told the painter to work back to front. Both are now fixed in the guide, and `block_in(direction=)` takes an angle.
7. **M6b — Darks. Done.** The palette bottomed out at value `0.23`, and the M6 pass built a tool around that (`compare()`'s `unreachable` split, finding 21) and a guide passage on compressing a reference's range to fit. A guide review before REHEARSAL4 called that an engine defect dressed up as a painting lesson, and it is right (`REVIEW.md` finding 33). The cause is not the mixing model but the pigment swatches: mixing in Kubelka-Munk space never takes a channel below the darker of its two ingredients, so nothing mixes darker than the darkest pigment, and `burnt_umber` at `#4A3728` reads `0.23` on its own. Real tube masstones are far darker, and real ultramarine and burnt umber mixed go close to black — that is the whole point of the mixture. **Decision taken: darken the masstones**, not add a black. Concretely:
   - **Darken the dark pigments** — `burnt_umber`, `ultramarine`, `alizarin`, `burnt_sienna`, `viridian`, and `cerulean` if the value scale asks for it — to values a swatch card of tube paint would show. The target is that `mix("ultramarine", "burnt_umber", 0.5)` reads at or near the model's own floor (the `0.01` linear reflectance floor from finding 5 is value about `0.10`), and that exercise 1's nine-step scale from the darkest mix to white has even steps in greyscale. Keep every channel above zero (finding 5: red + blue must still be violet) and re-check the mixes findings 5 and 6 were tuned against, because the power-mean exponent was chosen with the old swatches and may want revisiting. `rehearsal3/probe_value_floor.py` is the measurement.
   - **This moves every golden image and every rehearsal's colours, and that is accepted.** Regenerate the goldens once, deliberately, after looking at the sampler *and* a real painting with the new darks, not from the hash. The rehearsal scripts are a record and are not re-run.
   - **It interacts with item 11** (the wet-blend reflectance floor): darker pigments put more channels close to the `0.01` floor, so the soft-edge lightening that finding describes gets larger, not smaller. Measure it again after the darks land and decide whether item 11 moves up.
   - **Then take the workaround out.** `compare()` keeps its `unreachable` split for the few cells a photograph may still have below the model floor, but the guide's floor paragraph (step 3), `CALIBRATION.md`'s *Values* section, the *Reachable* paragraph under *Definition of done* below, and findings 21 and 33 are rewritten for the new range. The pass criterion goes back to being about every cell on the object.
   - **Before REHEARSAL4**, because that run's one question is about value, and running it against a palette about to be replaced measures a moving target (`NOTES.md`, gotcha 16).
   - **Landed.** The six darks are masstones now, and `REVIEW.md` finding 33 has the before/after table. `mix("ultramarine", "burnt_umber", 0.5)` reads `0.137` against the model's own `0.10`; the last three hundredths are hue, and not recoverable — a dark that is still blue cannot sit on the floor in all three channels, and pigments with no hue left break the mixtures findings 5 and 6 protect. The power-mean exponent moved `0.5` → `0.35`, for the reason this item anticipated: it had been set so that white carries a 50/50 mix about a quarter of the way up the palette's range, and widening the range left it crossing `0.158` of it. Exercise 1 now mixes to a *value* rather than to a ratio — equal white ratios cannot give even steps under this model at any exponent, and its nine bands now render `0.148`–`0.951` in steps of `0.100`. Every golden regenerated once, after looking at the sampler, the three `marks_*` cases, `drawing`, and a real painting rendered under both palettes. **Item 11 was re-measured and does *not* move up:** the prediction was that darker pigments would widen its soft-edge lift and the opposite happened, because the new swatches are written at or above the reflectance floor and nothing the model paints falls below it (`REVIEW.md`, the open entry after finding 32).
8. **M6c — Sweep.** `PAINTER.md` argues that a mass with a silhouette is laid as passes swept along its edge and stepped inward, not as a box and not as columns hung from the edge — and then hands the painter a fifteen-line recipe to retype (now in `CALIBRATION.md`, *Sweeping a shaped mass*). That is an API call (`REVIEW.md` finding 34). `s.sweep(edge, brush, color, depth=, size=, passes=, cross=...)`: `edge` is a list of normalised points along the boundary, each pass follows it offset one part-brush further into the mass, successive passes alternate direction as `block_in`'s do, and `cross=` lays a second set at an angle so the boundary closes up. It emits ordinary strokes, like `block_in`, so the log, undo and replay are right for free, and it is additive: no golden moves, one golden case is added for it. The boundary is the painter's own, so this is not the traced-copy question M8 reserves for the human — but the same rule as `sketch()` applies: a run that feeds `ref_outline(n)` straight into `sweep()` is an assisted mode and says so. The guide's *A region is a rectangle* paragraph becomes one call and the recipe leaves `CALIBRATION.md`. Small enough to land beside M6b, and worth having before REHEARSAL4 for the same reason.
   - **Done**, and additive as promised: no golden image moved and one was added, the log, undo and replay needed no changes, and the guide's paragraph is one call. Two things the recipe left open had to be decided — `into=` says which side of an open edge the mass is on rather than the engine guessing, and a pass that folds through the middle of a closed shape is dropped instead of scribbled. `REVIEW.md` finding 34 has the measurements; `CALIBRATION.md` has what a sweep costs and buys, in place of the recipe.
9. **M7 — Marks at detail scale.** The bristle comb prints the same streaks on every stroke, wider than an eye, so a detail stroke carries the brush's pattern and not the feature's. The golden-image tests from the start of M6 are the gate here: every change below regenerates them once, deliberately, with the change looked at. Vary the comb per stroke — spacing, phase, a few missing bristles — and scale the streaks with the brush size. Decide the pressure question here too. The evidence in `REVIEW.md` was about mark variety; the second rehearsal's eye test adds a sharper reason: pressure changes opacity and not width, so a lid line, a brow or a lash cannot taper, and every tapering mark is two strokes of different sizes. Width following pressure, at least for the round tips and with a floor of a pixel or two, is what features need. Give `dab()` a `press` argument (stamps on the same spot, default `1` so old logs replay unchanged): a single dab lands at about a third of its colour's strength, and a highlight the size of a catchlight needs three. All of this changes every stroke, so all of it is judged on the sampler *and* on the rehearsal copy, never the sampler alone.
10. **M8 — Non-rectangular masses.** Added after M6, and it goes before the server for the same reason M6 did: the server exposes the API and this changes it. Every named place in the API is an axis-aligned rectangle and the only helper named after a thing in the world is `horizon()`, so a band is the only mass `block_in` fills honestly. This is not cosmetic: given nothing but the engine's mechanical limits, six fresh sessions in eight justified their choice of subject by horizontal bands and rectangles in as many words (`rehearsal3/unprompted/`). Painters are reasoning their way to band-shaped pictures because that is what the tool can carry, and no amount of guide prose fixes it. `ref_outline(n)` already returns a polygon; a polygon region, and a `block_in` that fills one, is the change. It alters every painting, so it is judged on the sampler *and* a real painting, and it is partly the traced-copy question this brief reserves for the human.
11. **Also before the server: the wet-blend reflectance floor.** `blend_wet()` (`easel/color.py`) applies the Kubelka-Munk reflectance floor from finding 5 to the *existing* canvas colour before weighting by how much paint is actually landing, rather than after -- so a pixel at the soft edge of a dab, where only a percent or two of paint is depositing, still gets nudged toward the floor, and no pigment can ever paint truer than the floor allows even at full opacity. Found by an adversarial code review rather than by rendering and looking (`REVIEW.md`'s "Open, with evidence" entry after finding 32 has the reproduction, and the reason the floor itself can't just move: it is load-bearing for finding 5, so shrinking it risks reopening "red + blue comes out green"). The fix changes the wet-blend formula on effectively every soft dab edge in the engine, so treat it the way M6b, M7 and M8 are treated: judged on the sampler *and* a real painting, looked at, before any golden image is regenerated -- not a change to make from the hash alone.
12. **M9 — MCP server**, only if everything above is solid. One tool per CLI verb, plus `look`, `preview` and `compare` returning their images inline.

## Review loops (do these, don't skip them)

After M2 and again after M4, run an **adversarial review** in a separate reasoning pass: read the code and the guide as a hostile painter looking for reasons the output will look like clip-art. Typical findings to hunt for: strokes with identical edges everywhere, no variation in paint load, colours converging to mud, straight lines that are too straight, everything at the same opacity, a guide that describes functions but not painting. Write findings to `REVIEW.md`, fix them, note what changed.

Visual regression: golden-image tests for a fixed set of strokes. Property tests: strokes never write outside the canvas, undo restores exact state, replay from log reproduces the export byte-for-byte.

## Non-goals
- No GUI, no Krita/GIMP integration, no tablet input.
- No fluid simulation, no physically based watercolour.
- No image-to-image, no style transfer, no diffusion models anywhere in the pipeline. The point is that the strokes are chosen.
- Not pixel art. Not vector.

## Definition of done
A fresh session, given `PAINTER.md` and a reference photo, produces a recognizable copy in under 300 strokes without touching source code, then produces **two** paintings with no prompt. All exports plus their time-lapses exist. The engine's author has not seen the unprompted paintings before the human has.

**Two unprompted paintings, and the second must not repeat the first's composition.** One is not a sample. `rehearsal3/unprompted/` measured this: 63% of thirty-two fresh sessions named the same subject — a rain-wet street at dusk — before opening the guide, so a single unprompted painting says almost nothing about the painter, the guide or the engine, and two rehearsals running read meaning into exactly that. So:
- **The first is genuinely unprompted.** No constraint of any kind. This is the one place in the protocol where the painter chooses everything, and that is worth keeping intact.
- **The second must differ from the first in compositional structure**, and that is the only constraint. If the first is built from horizontal bands, the second must not be. Nothing is said about its subject, its palette, or what its marks should do — working out how is the part being measured, and `probe_axis_alignment.py` gives a number for whether it happened.
- Do **not** prescribe the solution — "make one line-based and the other curve-based", or any instruction about the marks. That hands over the artistic decision the stage exists to observe, and it invites marks chosen for their own sake, which the guide already warns against. Constrain the repeat, not the remedy.
- The second painting is therefore partly a capability probe rather than a free choice, and the write-up says so.

After M6 the protocol runs on two references. First an ordinary object, as this brief always asked — a mug on a table will do — and that run is the pass: the human recognises the object, `compare()` reports no **reachable** cell on it more than `0.10` from the reference's value, and the painter can point to strokes it rejected in `preview()` or `rehearse()` before painting them. Then the sitter, and that run is the measure of how far the tools reach: recognisable as the person or not, and the write-up says which features got there. After M7 the sampler and the rehearsal copy must still pass the golden-image tests, regenerated once, deliberately, with the change looked at.

**"Reachable" was load-bearing, and M6b has made it stop mattering.** The palette has no black, by the rule above, and as of M6 bottomed out at value `0.235` — measured, and unmoved by eight dried passes or four rounds of glazing (`rehearsal3/probe_value_floor.py`). A lamp-lit photograph does not: eighteen of the sitter's sixty-four cells were below anything a stroke could reach, that criterion was unmeetable on any dark reference, and two fresh sessions each spent about twenty-five strokes discovering it. M6b darkened the masstones and the box now floors at `0.13` — three hundredths off the model's own `0.10`, and those three are the hue the pigments carry. **The criterion is therefore every cell on the object, not `fixable`.** `compare()` keeps the `unreachable` split, but on the mug it should report none and on the sitter a handful at most; a run that finds more than that has found something about the reference, and the write-up says which cells and why.

The headline result is painted without `sketch(reference)`. The pencil is the painter's own — sketch first, look, adjust, then paint — and landmarks, preview and rehearsal are how it gets precision below a cell by its own seeing, which is the thing the copy stage measures. A run that starts from the machine-laid sketch is an assisted mode: worth running, reported separately, and never the number that says whether M6 is done, or the definition of done would be measuring the segmenter. The unprompted stage never receives a sketch it did not draw itself.
