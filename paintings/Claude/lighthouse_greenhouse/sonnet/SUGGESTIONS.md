# Suggestions from a sixth painting

Not a numbered session in the sense `../../../SUGGESTIONS.md` and `LESSONS.md` use the
word, and this file is not a request to merge into that register — it is one more data
point, left beside this painting for whoever next updates it to weigh.

The differences from the protocol matter, so they are stated up front rather than left
for a reader to discover: the subject (a lighthouse mid-conversion into a greenhouse) was
given, not chosen unprompted or against a reference photograph; nothing here was
re-measured the way `LESSONS.md`'s *check the painters' numbers* asks for; and this
session read `PAINTER.md`, `PAINTING.md`, `RECIPES.md`, `REFERENCE.md`, and — because the
subject was already decided — `paintings/Claude/lighthouse_dusk/` in full, before painting. It
did **not** open `CALIBRATION.md` until writing this file, and only then to check whether
what follows was already known. `../../../SUGGESTIONS.md` and `LESSONS.md` were both read
only after the painting was finished, at the request that produced this file — so nothing
below was written to match them, and where they already cover a finding it is said
outright rather than left for someone else to notice.

Everything below is **requested, not done**: no engine code was changed and no
documentation was edited to act on any of it. Several items are already-known,
already-open issues that this painting simply reproduced (good: a second data point on an
open item is evidence, per `LESSONS.md`'s own standard); a couple appear genuinely new;
one is a case where the existing design worked exactly as intended and is logged as such
because the file that would otherwise record that is this one.

Per `LESSONS.md`'s "check the painters' numbers": nothing here was reasoned back to a
mechanism and then trusted. Where a mechanism is guessed at, it is labelled a guess.

## The engine

| What was found | Status against the existing record | Suggestion |
|---|---|---|
| `block_in(tower_shape, ..., edge="clean")` on a polygon tapering sharply (base **0.20** wide, top **0.07** wide, four points) drew a tall pointed arch above the flat top that is nowhere in the polygon — not a rounded corner, a full overshooting loop, several percent of the shape's own height tall. Dropping `edge="clean"` for the default ragged edge removed it outright; never retried on the lantern or roof, which are similarly narrow. | **Extends an open item.** `../../../SUGGESTIONS.md`'s third session already found `edge="clean"`'s contour reads back with rounded knobs at corners under a wide brush, and traced it to the sweep's wander rather than the brush's jitter — logged there as unresolved ("the remaining error is the outline's own corners under a wide brush"). My brush (`size=0.02`) was not obviously wide relative to the shape, and the result was a loop, not a knob — the variable that seems to matter here is how *close together* two corners of the outline are, not the brush's width alone. **Observed only; I did not instrument it.** | Measure the sweep's contour as the distance between two consecutive outline corners shrinks relative to brush size, on a shape that narrows a lot (not just a uniform band with one odd corner) — I'd guess the failure is closer to a hairpin turn in the offset curve than to a single corner's rounding, but that is exactly the kind of guess `LESSONS.md` says to measure rather than trust. If confirmed, either miter/clamp the sweep's turn there, or have `edge="clean"` warn when two corners of the given outline are closer together than some multiple of the brush size. |
| A wedge shape (mouth **~0.045** wide, far edge **~0.42** wide) given to `scumble(..., direction="vertical")` with no `size=` bloomed at the narrow end and read as barely-there at the wide end, rather than tapering. | **Stresses a fix past where it was tuned.** The `3 × extent / n` auto-size is the fourth session's own fix (`../../../SUGGESTIONS.md`), built and measured against roughly uniform-width bands. It has no way to know a shape's *local* width varies 9× along the direction it steps, and one global `extent` can't serve both ends of that. **Observed only** — abandoned after one rehearsal for a hand-built five-trapezoid version, each segment sized to its own local width, rather than instrumented further. | Either teach the auto-size (or its warning) to look at the shape's width at both ends of the stepping axis and say so when they differ by a lot — "this place's width varies Nx along the direction `scumble` steps; `size=` picked for one end will be wrong for the other" — or leave it and add exactly that sentence to `RECIPES.md`'s "a passage light in the middle" / `PAINTING.md`'s scumble-sizing note, next to the existing "leave size off" advice, so a painter reaches for a hand-built version *before* rehearsing the wrong one. |
| A `pressure` list meant to taper width (`pressure=[1.0, 0.35]`) on a `flat` brush did nothing to the width — every pot came back a rectangle with chisel ends, exactly `PAINTING.md`'s own "a short flat or knife stroke is a rectangle" / "small accents want round_hard" passage, **which I had already read**, once as part of `PAINTING.md` and again inside `RECIPES.md`'s "a form that turns." | **Docs are already correct and I ignored them anyway** — which is the exact, named pattern `PAINTER.md` opens "What you are bad at" with, and the one `LESSONS.md` calls *warning is not method* elsewhere in the same repo. | This is an engine request, not a docs request, on purpose: given a pressure list with more than one distinct value, `flat`/`bristle`/`knife` could emit the same kind of one-line warning `smudge`'s size and `cost`'s budget already do — *"pressure=[...] on a flat/bristle/knife tip changes paint, not width — round_hard tapers width."* It is exactly the shape of check `LESSONS.md` already proposes building ("a check the tool runs over the pass it just painted") and not yet built; consider it a second candidate rule alongside the ones already listed there. |
| `bristle` at `size≈0.008–0.016` (the climbing vine tendrils, the pots' trailing plants) was nearly invisible on first rehearsal — `round_hard` at the same sizes read fine. | **Already documented, and already on `LESSONS.md`'s own candidate-check list** verbatim ("a `bristle` under `size=0.025`"), which that file says is not yet built. | Nothing new to request except a second, independent case for the pile: this is a real pass of a real painting the candidate check would have caught, which is the bar `LESSONS.md` sets for building one. |
| Two mixtures — a rock plane and the light beam — were each mixed once, checked only against a target `value_of()` (and, for the beam, its `hex()`, printed as `PAINTING.md` says to before painting a field of a colour), and both rendered far more saturated in a large flat plane against this picture's very cool, very desaturated field than either number suggested. Both needed a second and third desaturation pass, found only by rehearsing them at real scale next to what they'd actually sit beside. | **Possibly new** — I did not find this in `../../../SUGGESTIONS.md` or `LESSONS.md`. **Observed twice; mechanism is a guess** (simultaneous contrast: the same chroma reads more vivid against a low-chroma field than it would against a varied one), **not measured**. | Per *measure the mechanism, not the failure*: before building anything, render one fixed chroma against fields of a few different mean chromas and see whether perceived vividness actually tracks the field the way I'm assuming. If it holds, the instrument I'd want is a `palette.chroma_of(c)` beside `value_of`, and a line at `p[name] = ...` time comparing a new mixture's chroma against the palette's existing named slots — not a rule in the guide, an instrument, in the spirit of `sample(rendered=True)` answering "does this look like what I think it looks like" as a line instead of a belief. |
| Inside a script run as a lone `easel run session.easel onepass.py --rehearse` (not chained with the passes before it), `s.stroke_count` and `s.remaining` read `0` and the full budget from *inside the script*, while the same rehearsal's `compare()` and `look()` plainly operated on the real, already-painted canvas (compare reported real painted values, not bare-ground ones). Worked around by trusting the CLI's own "Rehearsed X.py: N of M left" line instead, which was correct throughout. | **Not found in either file; not root-caused.** I did not read `session.py`, so this could be `scratch()`/the rehearsal copy not carrying over `History`'s budget bookkeeping, or something specific to a single-script `--rehearse` versus the full-chain form — I only ever ran the single-script form on an already-committed session. | Worth a look by whoever has the source open: does `Session.scratch()` (or whatever `--rehearse` builds internally for one script against an existing `.easel`) copy the budget/stroke-count state the way it copies the canvas and RNG stream? If this is already known behaviour (e.g. "budget is a CLI-level concept for a --rehearse'd chain and never was session-internal for a lone script"), it's a one-line addition to `REFERENCE.md`'s budget section rather than a bug. |
| A switchback stair, drawn as one bent `ribbon` through six points, cost 141 of a 340 budget before a stroke was spent — cut into five straight flights (each a `stroke()`, per "a mass much longer than it is wide is a stroke"), the same stair cost five. | **Not a new finding — logged as a hit, not a miss.** This is `PAINTING.md`'s own worked example ("a painter budgeted 4 and paid 21") almost exactly reproduced, and `s.cost()` caught it for free before anything was spent, precisely as designed.
